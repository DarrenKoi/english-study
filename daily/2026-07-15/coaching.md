## 한글→영어

### 카드 1 — 규칙을 "자세히" 알고 싶다   (내가 쓴 한글)

- 내가 쓴 한글: "영어 관사, 정관사 붙이는 규칙을 자세히 알고 싶어."   (출처: spool:spool/궁금한점.txt)
- 자연스러운 영어:
  - (중립) **I want to understand the rules for English articles — especially when to use the definite article.**
  - (격식·수업/멘토 요청) **Could you walk me through how English articles work, particularly the rules for the definite article?**
  - (회화) **I want to get my head around English articles — mainly when "the" goes in.**
- 왜 이렇게:
  - **"자세히 알고 싶어" ≠ "know in detail"** — 한국어의 "자세히 알다"는 영어로 `know in detail` 이 아니라 보통 **`understand`** 한 단어로 흡수됩니다. `know` 는 "사실을 알고 있다"(정보 보유)이고, 규칙의 **작동 원리**를 익히고 싶은 것이므로 `understand` 가 정확합니다. 굳이 "자세히"를 살리려면 `understand ... properly` 나 `get a proper handle on ...`.
  - **`the rules for X` vs `the rules of X`** — 문법 규칙처럼 **"X를 다루는 방법"**이면 `rules for`, **"X 안에 내재된 규칙"**이면 `rules of`. 관사 사용법은 전자입니다.
  - **`walk me through ~`** — "차근차근 설명해 주다". 배우는 사람이 쓰기에 가장 자연스러운 요청 동사구입니다. `explain me` 는 **비문**입니다 (❌ `explain me the rules` → ✅ `explain the rules to me`).
  - **역설적 포인트**: 이 문장을 영어로 옮기는 순간 `**the** rules`, `**the** definite article` 처럼 **관사가 필요**해집니다. 관사를 묻는 문장조차 관사 없이는 못 씁니다 — 오늘 spool 답변이 바로 그 이야기입니다.

### 카드 2 — "a, an 붙이는 규칙도"   (내가 쓴 한글)

- 내가 쓴 한글: "a, an을 붙이는 규칙도 알고 싶고"   (출처: spool:spool/궁금한점.txt)
- 자연스러운 영어:
  - (중립) **I'd also like to know when to use "a" versus "an".**
  - (격식) **I would also appreciate a breakdown of the rules governing "a" and "an".**
  - (회화) **And while you're at it, how do I pick between "a" and "an"?**
- 왜 이렇게:
  - **"붙이는 규칙" → `when to use`** — 한국어는 "규칙"이라는 명사로 묻지만, 영어는 **`when to + 동사`(의문사 + to부정사)** 로 묻는 것이 훨씬 자연스럽습니다. `the rules for attaching a/an` 은 문법적으로 맞지만 **번역투**로 들립니다. 영어는 "규칙이 무엇인가"보다 **"언제 쓰는가"**로 질문을 구성합니다.
  - **`A versus B`** — 두 선택지의 갈림을 물을 때 `versus`(또는 `vs.`)가 가장 간결합니다. `the difference between A and B` 도 좋지만 조금 더 깁니다.
  - **`~도` → `also` 의 위치**  — `I'd **also** like to know ~`. 조동사(`'d`) 뒤, 본동사(`like`) 앞이 표준 위치입니다. 문장 맨 앞의 `Also, ...` 는 회화에서는 괜찮지만 격식 문어에서는 다소 느슨합니다.
  - **`while you're at it`** — "하는 김에". 부탁을 하나 더 얹을 때 쓰는 매우 구어적인 완충 표현입니다. 동료·친구에게는 좋지만 상사·고객에게는 쓰지 마세요.

### 카드 3 — "예외 케이스가 있는 지도 알려줘"   (내가 쓴 한글)

- 내가 쓴 한글: "예외 케이스가 있는 지도 알려줘."   (출처: spool:spool/궁금한점.txt)
- 자연스러운 영어:
  - (중립) **And let me know if there are any exceptions.**
  - (격식) **Please also flag any edge cases where the rule breaks down.**
  - (회화) **Oh, and are there any gotchas?**
- 왜 이렇게:
  - **`exception` vs `edge case` vs `gotcha`** — 세 단어가 미묘하게 다릅니다.
    - `exception` = **규칙 자체가 적용되지 않는** 경우 (an hour — h가 묵음).
    - `edge case` = 규칙은 살아 있으나 **경계에서 판단이 어려운** 경우 (an SSD? a SSD?).
    - `gotcha` = **틀리기 쉬운 함정** (구어. "아 속았다!"의 gotcha에서 옴). 개발자들이 매우 자주 씁니다.
    - 당신이 물은 것은 정확히 **`exception`** 이지만, 실무 대화에서는 `gotcha` 가 더 생생합니다.
  - **`any` 의 필수성** — 의문·조건절에서 "혹시 ~가 있는지"는 **`any`** 를 씁니다. `if there are exceptions` 도 되지만, `any` 가 들어가야 **"있든 없든 알려달라"**는 열린 질문이 됩니다.
  - **`where the rule breaks down`** — "규칙이 무너지는 지점". `break down` 은 "고장 나다"에서 확장돼 **"이론·규칙이 더는 통하지 않다"**는 뜻으로 격식 문어에서 자주 쓰입니다. `exception` 을 동적으로 표현한 고급 대안입니다.
  - **한국어 원문의 오타** — "있는 지도" 는 "있는**지도**" 가 맞습니다 (`-는지` 어미 + 보조사 `도`). 의존명사 `지`(시간 경과: "떠난 지 3년")와 어미 `-는지`(여부)는 다릅니다.

## 영어 다듬기

### 카드 4 — 산문에서 관사를 빼면 안 되는 자리

- 내가 쓴 영어: "Primary risk for a docs task is INACCURACY — documentation that contradicts the shipped code."   (출처: transcript:[user] auto_recipe_creator 리뷰 지시문)
- 정정: **`Primary risk` → `The primary risk`.**
  단수 가산명사(`risk`)는 맨몸으로 설 수 없습니다. 그리고 여기서는 **`primary`(가장 주된)** 라는 **유일성 형용사**가 붙어 있으므로 `a` 가 아니라 반드시 **`the`** 입니다. (최상급·서수·`primary`·`main`·`only` → 항상 `the`)
- 더 나은 표현: **The primary risk in a docs-only task is inaccuracy — documentation that contradicts the code that actually shipped.**
- 왜:
  - **`risk for` → `risk in`** — 위험이 **어디에 내재하는지**를 말할 때는 `in`(그 작업 안에 도사린 위험). `risk for` 는 "누구에게 위험한지"(대상)를 가리킵니다: `a risk for junior developers`.
  - **전부 대문자 `INACCURACY` → 소문자** — 강조하고 싶은 마음은 알겠지만, 격식 문어에서 전부 대문자는 **소리 지르는 것**처럼 읽힙니다. 이미 `The primary risk ... is inaccuracy` 라는 문장 구조 자체가 그 단어를 주역으로 세우고 있으니, 대문자는 불필요합니다. 정 강조하려면 이탤릭(`*inaccuracy*`)이 격식에 맞습니다.
  - **`the shipped code` → `the code that actually shipped`** — `shipped code` 도 통하지만, 관계절로 풀면 **`actually`(실제로)** 를 넣을 자리가 생겨 "문서가 주장하는 코드 vs 진짜 나간 코드"의 **대비**가 살아납니다. 이 문장의 논지가 바로 그 대비이므로, 구조가 논지를 받쳐줍니다.
  - **참고**: 이 문장은 목록·제목이 아니라 **산문**이므로 관사가 필수입니다. 같은 문서의 제약 목록(`- Korean comments where surrounding code is Korean;`)에서 관사를 뺀 것은 **전보체(telegraphic style)로 올바른 선택**입니다. 두 문체를 구분하는 감각이 오늘 spool 답변의 핵심이기도 합니다.

### 카드 5 — 명령을 더 날카롭게

- 내가 쓴 영어: "Treat the report as unverified claims; verify against the diff."   (출처: transcript:[user] auto_recipe_creator 리뷰 지시문)
- 정정: (문법 오류 없음)
- 더 나은 표현: **Treat the report as claims to be verified, not as a record of what shipped. Verify every one of them against the diff.**
- 왜:
  - **`unverified claims` → `claims to be verified`** — 원문은 보고서의 **현재 상태**(아직 검증 안 됨)를 말합니다. 개선안은 리뷰어의 **의무**(반드시 검증해야 할 것)를 말합니다. 지시문의 목적은 상태 서술이 아니라 **행동 유도**이므로, `to be p.p.`(당위의 부정사)가 목적에 더 정확히 봉사합니다.
  - **`not as a record of what shipped` 추가** — 영어 지시문의 강력한 패턴은 **`as A, not as B`** 입니다. **틀린 해석을 명시적으로 차단**해야 지시가 새지 않습니다. 오늘 배치의 다른 문서에도 같은 구조가 있습니다: *"the implementation is wrong, not the expectation."*
  - **세미콜론 → 마침표** — 세미콜론은 두 절을 **대등하게** 잇습니다. 그런데 여기서 뒤 절(`verify against the diff`)은 앞 절의 부연이 아니라 **핵심 명령**입니다. 문장을 끊고 독립시켜야 무게가 실립니다.
  - **`every one of them` 추가** — 원문의 `verify against the diff` 는 *무엇을* 검증하는지가 비어 있습니다. 목적어를 명시하면 **빠져나갈 구멍이 없어집니다.**

### 카드 6 — "주변과 맞춘다"를 정확히

- 내가 쓴 영어: "Korean style matches surroundings; markdown in CLAUDE.md is well-formed."   (출처: transcript:[user] auto_recipe_creator 리뷰 지시문)
- 정정: **`matches surroundings` → `matches the surrounding code`.**
  `surroundings`(복수 명사, "주변 환경")는 보통 **물리적 환경**을 뜻합니다 (`He looked around at his surroundings.`). 코드 문맥에서는 **형용사 `surrounding` + 명사**가 정확합니다: `the surrounding code`, `the surrounding comments`.
- 더 나은 표현: **The Korean comments read consistently with the surrounding code, and the markdown in `CLAUDE.md` is well-formed.**
- 왜:
  - **`match` → `read consistently with`** — `match` 는 "일치한다"(형태적 동일)에 가깝습니다. 문체는 똑같을 수 없고 **어울리기만** 하면 되므로, `read consistently with`(~와 일관되게 읽힌다)나 `is consistent with` 가 실제 의도에 맞습니다. `read` 를 **자동사("~하게 읽힌다")**로 쓰는 이 용법은 문체 평가에서 아주 유용합니다: *"The comment reads awkwardly."*
  - **`Korean style` → `The Korean comments`** — 검사 대상은 추상적인 "스타일"이 아니라 **구체적인 주석**입니다. 리뷰 항목은 **검증 가능한 대상**을 가리켜야 합니다.
  - **세미콜론 → `, and`** — 이 두 항목은 대조·부연 관계가 아니라 그냥 **병렬 체크 항목**입니다. 병렬에는 `and` 가 자연스럽고, 세미콜론은 **의미적 긴장**이 있을 때 아껴 씁니다.
  - **역시 관사** — `the surrounding code`, `the markdown in CLAUDE.md`. 둘 다 **"이 프로젝트의 그것"** 이라 특정 가능하므로 `the` 입니다 (spool 답변 §2-(2) 상황상 유일).
