## 영어 다듬기

### 카드 1 — 승인하고 커밋 지시
- 내가 쓴 영어: "good. commit and push" / "commit and push"   (출처: transcript:[user] auto-recipe-creator, skewnono-v3-nuxt)
- 더 나은 표현: Looks good. Go ahead and commit and push.
- 왜: 짧은 지시라 틀린 건 없다. `Looks good.` 가 `good.` 보다 "검토했고 만족한다"는 뜻을 분명히 한다. `Go ahead and + 동사` 는 허락하는 뉘앙스라 명령조가 누그러진다. 문장 첫 글자는 대문자.

### 카드 2 — 중복 내용은 링크로
- 내가 쓴 영어: "also AGENTS.md should be updated. make a link to CLAUDE.md if there are duplicated contents"   (출처: transcript:[user] skewnono-v3-nuxt)
- 정정: `duplicated contents` → `duplicate content`. "내용"이라는 뜻의 `content` 는 불가산이라 `-s` 를 붙이지 않는다(`contents` 는 목차·내용물).
- 더 나은 표현: AGENTS.md needs updating too. Wherever it repeats CLAUDE.md, replace that part with a link to CLAUDE.md.
- 왜: `needs updating` 은 `should be updated` 보다 짧은 구어형이다. `if there are …` 보다 `Wherever it repeats …` 가 "겹치는 곳마다"라는 범위를 정확히 짚는다. `make a link` 는 뜻은 통하지만 `replace … with a link` 가 무엇을 없애고 무엇을 넣는지 다 말해 준다.

### 카드 3 — 사무실에 돌아왔다
- 내가 쓴 영어: "i am back to office"   (출처: transcript:[user] skewnono-v3-nuxt)
- 정정: `i` → `I`. `back to office` → `back at the office` (또는 `back in the office`). 이미 도착한 상태는 `at`, 향하는 중이면 `to`. 특정 사무실이라 `the` 도 필요하다.
- 더 나은 표현: I'm back at the office.
- 왜: `back to the office` 는 `I'm going back to the office` 처럼 이동 동사와 쓸 때 맞는다.

### 카드 4 — 새 폴더 구조로 실행했더니
- 내가 쓴 영어: "and run with new folder named structure and found opensearchpy.exceptions.connectionError as so on."   (출처: transcript:[user] skewnono-v3-nuxt)
- 정정: `run` → `ran` (이미 한 일이라 과거형, `found` 와 시제 맞춤). `new folder named structure` → `the renamed folders`. `as so on` → `and so on`. 예외 이름은 대소문자까지 그대로 `ConnectionError`.
- 더 나은 표현: I ran the app from the renamed folders and got `opensearchpy.exceptions.ConnectionError`, among other errors.
- 왜: 에러는 `find` 보다 `get` 이나 `hit` 이 자연스럽다. `and so on` 을 문장 끝에 붙이는 대신 `among other errors` 로 "다른 에러도 있었다"를 분명히 했다.

### 카드 5 — 왜 그런가
- 내가 쓴 영어: "why is it so?"   (출처: transcript:[user] skewnono-v3-nuxt)
- 더 나은 표현: What's causing this?
- 왜: `Why is it so?` 는 문법상 틀리지 않지만 예스럽고 교과서처럼 들린다. 원인을 묻는 개발 대화에서는 `What's causing this?` 나 `Why is that?` 이 보통이다.

### 카드 6 — 이미 지웠는데 되살리려면
- 내가 쓴 영어: "I have deleted old folders already. how can I put them back?"   (출처: transcript:[user] skewnono-v3-nuxt)
- 정정: `old folders` → `the old folders` (앞서 말한 바로 그 폴더라 `the`).
- 더 나은 표현: I've already deleted the old folders. Is there any way to get them back?
- 왜: `already` 는 `have` 와 과거분사 사이가 가장 자연스럽다. `put them back` 은 "제자리에 다시 놓다"이고 사라진 걸 되찾는 뜻에는 `get them back` 이나 `restore them` 이 맞는다. `Is there any way …?` 가 "방법이 있기는 한가"라는 걱정까지 담는다.

### 카드 7 — 실행했는데 여전히 mock
- 내가 쓴 영어: "run setup_office_adapters and when I visit the localhost:3000 still it loads the mock data."   (출처: transcript:[user] skewnono-v3-nuxt)

- 왜: 기대와 다른 결과라 `and` 보다 `but` 이 맞는다. 페이지를 주어로 세우면 `when I visit` 절이 필요 없어진다.

### 카드 8 — 사무실 PC 에 있다

### 카드 21 — 모든 경우를 다루게

### 카드 22 — 출력이 바뀌면 곤란하다
- 내가 쓴 영어: "if output changes, we fix many code base in other projects. so better to keep functions output unchanged if possible"   (출처: transcript:[user] equipment-data-map)

- 더 나은 표현: If the output changes, we'd have to fix code in several other projects, so it's better to keep the functions' output unchanged if we can.
- 왜: `so better to …` 는 주어·동사가 빠진 메모체다. `it's better to …` 로 완성한다. 두 문장이 원인과 결과라 `so` 로 한 문장에 이어도 된다.

### 카드 23 — 기존 코드는 건드리지 않고

- 왜: 제안이라 `can` 보다 `could` 가 부드럽다. 괄호 속 조건을 `ideally` 로 본문에 넣으면 우선순위가 분명해진다. `leave … untouched` 는 "손대지 않은 채로 두다"라는 정석 표현.
